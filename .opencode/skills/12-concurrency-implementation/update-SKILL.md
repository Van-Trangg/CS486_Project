# 3. Required final workflow architecture

The final database workflow should have two protected entry points with clearly separated responsibilities.

```text
Application
    |
    v
sp_SubmitBooking
    |
    |-- creates the booking row
    |-- determines resolution_path
    |-- stores required advisory acknowledgements
    |
    +-- Instant
    |      |
    |      v
    |   sp_ApproveBooking
    |      |
    |      v
    |   Approved
    |
    +-- Staff
           |
           v
         Pending
           |
       staff decides later
           |
           v
    sp_ApproveBooking
           |
           v
        Approved
```

Required responsibility split:

```text
sp_SubmitBooking
= the only normal application entry point that INSERTs a booking
= derives Instant versus Staff
= assigns resolution_path once
= records advisory acknowledgements
= invokes protected approval immediately for Instant bookings

sp_ApproveBooking
= the only normal application entry point that changes a booking into Approved
= performs the concurrency-safe approval checks
```

Do not duplicate the approval logic in `sp_SubmitBooking`.

# 5. `sp_SubmitBooking` must become the sole booking-creation path

The current pattern:

```text
application INSERTs BOOKING
→ calls sp_SubmitBooking(@BookingId)
```

must be removed from the normal application workflow.

The updated procedure should no longer depend on a booking row already existing.

Instead:

```text
application
→ EXEC sp_SubmitBooking(...)
→ procedure itself INSERTs dbo.BOOKING
```

Use the exact booking attributes required by the actual schema.

The procedure signature must therefore accept the data required to create a booking, such as the actual equivalents of:

- requester
- space
- requested start
- requested end
- expected participants
- purpose
- any other required non-derived booking fields

Do not blindly use these example parameter types; inspect the schema first.

If `booking_id` is generated by SQL Server, use the project’s actual identity/key-generation mechanism, for example:

```sql
SET @BookingId = SCOPE_IDENTITY();
```

If the application supplies the booking ID by approved design, accept it explicitly instead.

```text
→ resolution_path = 'Instant'

otherwise
→ resolution_path = 'Staff'
```

Use the exact role and space-type values from the approved schema.

# 7. Assign `resolution_path` exactly once

The updated workflow should determine the path **before the booking is inserted** and INSERT the correct value immediately.

Preferred pattern:

```text
determine path first
→ INSERT booking with:
   resolution_path = Instant
or
   resolution_path = Staff
```

Do not use the old staging pattern:

```text
INSERT resolution_path = Staff
→ later change Staff to Instant
```

because the approved rule makes `resolution_path` immutable after assignment.

After creation, the database must prohibit unauthorized transitions such as:

```text
Instant → Staff
Staff → Instant
Instant → NULL
Staff → NULL
```

Use the enforcement mechanism already approved by Steps 9–11.

# 8. `sp_SubmitBooking` must lock SPACE before inserting BOOKING

Preserve the Step 11 lock order.

The procedure should conceptually perform:

```text
BEGIN TRANSACTION
→ lock SPACE
→ read authoritative SPACE / requester data
→ determine resolution path
→ validate submission
→ INSERT BOOKING
→ INSERT required acknowledgements
→ if Instant, invoke protected approval
→ COMMIT
```

The transaction must begin before the protected `SPACE` lock is acquired.

Use the approved per-space lock, normally:

```sql
SELECT ...
FROM dbo.SPACE WITH (UPDLOCK, HOLDLOCK)
WHERE space_code = @SpaceCode;
```

Do not:

```text
INSERT BOOKING
→ then lock SPACE
```

because that reverses the intended lock order and increases deadlock risk.

Required lock order:

```text
SPACE
→ BOOKING
→ BOOKING_ADVISORY_ACK / related rows
```

Maintenance escalation must remain compatible with the same per-space ordering.

Use the actual approved type/object names.

The final acknowledgement set must exactly match the applicable active overlapping advisory set when the submission is resolved:

- no missing required advisory

- same space
- active/open maintenance status as defined by the project
- `impact_level = 'advisory'`
- correct time overlap

Insert acknowledgement rows for both Instant-path and Staff-path bookings whenever applicable.

Do not make acknowledgements an Instant-only concept.

# 10. Instant bookings must be approved immediately

For an Instant-eligible booking:

```text
sp_SubmitBooking

→ INSERT acknowledgements
```

`sp_SubmitBooking` must not directly duplicate all approval update logic.

The approved-state transition should remain centralized in:

```sql

```

This makes `sp_ApproveBooking` the sole normal application path into `Approved`.

# 11. Staff bookings remain Pending

For a booking that does not qualify for Instant resolution:

```text
resolution_path = 'Staff'

```

Do not automatically approve it.

Later staff decision:

```text

→ EXEC dbo.sp_ApproveBooking
→ protected approval
```

The resolution path should remain `Staff`.

# 12. `sp_ApproveBooking` must support both standalone and caller-owned transactions

Because Instant submission may call:

```sql
EXEC dbo.sp_ApproveBooking ...
```

from inside the transaction owned by `sp_SubmitBooking`, `sp_ApproveBooking` must not blindly reject every caller transaction.

Remove patterns such as:

```sql
IF @@TRANCOUNT <> 0
    THROW ...
```

when they prevent the approved nested workflow.

Implement safe transaction ownership.

Conceptually:

```sql
DECLARE @StartedTransaction BIT = 0;

IF @@TRANCOUNT = 0
BEGIN
    BEGIN TRANSACTION;
    SET @StartedTransaction = 1;
END;
```

Only commit when the procedure itself started the transaction:

```sql
IF @StartedTransaction = 1
    COMMIT TRANSACTION;
```

For error handling, preserve the caller’s transaction semantics and do not incorrectly commit or roll back work owned by another procedure.

An equally safe shared-core design is acceptable if already approved, but there must still be one protected approval implementation used by both Instant and Staff paths.

# 13. `sp_ApproveBooking` must remain concurrency-safe

Whether called:

```text
from sp_SubmitBooking for Instant
```

or:

```text
directly for later Staff approval
```

it must preserve the same Step 11 invariant:

> Two occupying bookings must never use the same space during overlapping time periods.

Required protected sequence:

```text
transaction exists / begin transaction
→ acquire same SPACE lock
→ fresh authoritative booking read
→ verify booking is still approvable
→ verify resolution-path semantics
→ recheck occupying-booking overlap
→ recheck Out-of-Service maintenance
→ verify required acknowledgement state
→ UPDATE booking to Approved
→ commit only if procedure owns the transaction
```

No human wait or external call may occur while locks are held.

# 14. Restore the full Phase 1 occupying-status rule

This is a required correction.

The approved Phase 1 baseline treats both:

```sql
'Approved'
'Checked In'
```

as occupying the space.

Every conflict check in Step 12 must therefore use:

```sql
booking_status IN ('Approved', 'Checked In')
```

not:

```sql
booking_status = 'Approved'
```

Apply the same occupying-status set consistently in:

- `sp_SubmitBooking` where a conflict check is still needed
- `sp_ApproveBooking`
- overlap-trigger backstop
- any other protected availability check in Step 12

When checking an existing booking being approved, exclude the current booking:

```sql
b.booking_id <> @BookingId
```

Use the same half-open overlap predicate everywhere:

```sql
existing_start < requested_end
AND existing_end > requested_start
```

This must:

- reject true overlaps;
- allow adjacent intervals;
- prevent approval over a `Checked In` booking.

Do not silently weaken the Phase 1 occupancy rule.

# 17. Direct INSERT bypass must be closed

This is a blocking correction.

Once `sp_SubmitBooking` becomes the only normal application booking-creation path, the application role must not be able to directly insert arbitrary rows into `dbo.BOOKING`.

Where `AppServiceRole` exists, enforce:

```sql
DENY INSERT
ON OBJECT::dbo.BOOKING
TO AppServiceRole;
```

Then grant:

```sql
GRANT EXECUTE
ON OBJECT::dbo.sp_SubmitBooking
TO AppServiceRole;
```

This prevents an application caller from bypassing the per-space protocol by directly inserting:

```text
booking_status = Approved
```
